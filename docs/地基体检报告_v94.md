## 二、三大结构级发现

### F1 · 发布文件 CRLF 虚增（预算门误报根因）

- **根因**：`git config core.autocrlf = true` 且仓库**无 `.gitattributes`**。git 检出/变基（rebase/checkout/clone）时把发布文件转成 CRLF；git 索引中存的实际是 CRLF（历史以 CRLF 入库），导致"工作区 LF 产物"与"索引 CRLF"互相污染。
- **实测**：game.html/game_check.html/game_built.html 各 115,917 个 CRLF；game_chunked.html/index.html 各 87,489 个 CRLF。LF 版本应为 10,066,529B / 7,337,737B，CRLF 后 10,182,446B / 7,425,226B（game.html 虚增 **115,917B**）。
- **后果**：本地 `elda ci` 预算门会把 CRLF 体积当真值 → **误报超预算 FAIL**（当前工作区即处于此状态）；四路字节比较在 git 层反复漂移。
- **修复方案（二选一，推荐 A）**：
  - A（推荐）：新增 `.gitattributes`（`*.html text eol=lf`、`src/**/*.js text eol=lf`、`chunks/*.js text eol=lf`）+ 一次性 `git add --renormalize` 提交。此后本地/CI 全 LF，体积稳定，预算门真实。
  - B：`git config core.autocrlf false`（只治本机，不治 CI/克隆）。
  - 已备工具：`tools\normalize_lf.py`（幂等转 LF；`--check` 只查不改；`--publish` 只转 5 个发布文件）。
  - **执行前注意**：renormalize 会产生一次性大 diff（纯换行），属"地基修复批"，建议独立提交并跑完整验证链。

### F2 · 单文件版缺分片节点（双版本不一致）

- **机制**：v62 分片机制把一批节点从 `src/script_02*.js` 移入根目录 `chunks/v62_*.js`（如学院 `academy_*` 269 个）。但构建脚本 `_build_authority.py build` **只拼接 `src/script_*.js + gap + data_nodes`，不含根目录 chunks**。
- **实测**（浏览器运行时）：
  - 分片版 `game_chunked.html`：window.N = **5,593** 键（academy_=269，全量）。
  - 单文件版 `game.html`：window.N = **3,883** 键（academy_=0，缺分片节点）。
- **影响**：线上（GitHub Pages = index.html = 分片版）**全量正常**；本地双击 `game.html`（单文件版）会缺学院等分片内容（部分 travelTo 可能空节点）。
- **为什么之前没发现**：`elda ci` 统计 src+chunks 全量（5,580）全绿；四路字节只保证 `game=game_check`、`chunked=index` 两两一致，**从不校验"单文件版节点覆盖 == 全量"**。
- **修复方案（推荐）**：`_build_authority.py build` 在 data_nodes 注入后追加根目录 `chunks/v62_*.js` 内容（幂等：无 chunks 则跳过）→ 单文件版=全量。预计单文件版体积 +~1.7MB，需 `elda budget --reason` 上调 `game_html_bytes_max`（如 10.12MB → 12.5MB）。此批属"地基修复批"，改构建链需备份+完整验证链（build→copy→chunks→sync→ci→smoke→bu 三档）。
- **可选**：新增检查器 `c_nodecover`（发布文件内嵌节点数 == elda 全量节点数，允许阈值差），把"单文件版缺节点"变成 ci FAIL。

### F3 · V35 遗留报错刷屏（无功能影响）

- **现象**：console 27 条 `[V35] Module not found: core`（每次加载 12~27 条不等，与加载时序相关）。
- **定位**：`src/script_00.js` 与 `src/script_04.js` **重复定义** `v35_arch_init`（同名函数，后者覆盖前者）；部分早期 `load('core')` 调用发生在模块注册之前 → 报错。运行时实测 `V35_ModuleManager.modules` 中 core/ui/save/battle/magic/faction **全部 loaded=true**，手动 `load('core')` 返回 true，**游戏功能零影响**。
- **修复方案（可选，低优先）**：删除 `script_00.js` 中重复的 `v35_arch_init` 定义（保留 script_04.js 全量版），或给 `load()` 加幂等静默。属引擎层小改，建议与 F1/F2 同批做并跑全验证链。

## 三、上限与内存分析（回答"如何安全大量扩充"）

### 3.1 内存根本不是瓶颈

- `performance.memory` 实测：used≈18.2MB / total≈21.7MB / **limit≈3.76GB**。当前全量节点（5,593）运行时仅占 18MB。
- 线性外推：即使节点翻 10 倍（5.5 万节点）、文本 100MB 级，运行时内存仍 < 300MB，远低于 3.76GB 上限。**内存维度可支撑远超当前的规模。**

### 3.2 真正的硬瓶颈：单文件版体积预算

| 版本 | 当前（LF） | 预算上限 | 余量 |
|---|---|---|---|
| game.html（单文件） | 10,066,529B | 10,120,739B | **54,210B（约 5%）** |
| game_chunked.html（分片） | 7,337,737B | 8,500,000B | 1,074,774B（约 13%） |

- 单文件版余量不足 5%：再写 2~3 批内容就顶穿。
- 分片版余量约 1.07MB：还能容纳约 15 万字节内容（约 3~4 批 250 节点级内容包）。

### 3.3 扩容安全策略（推荐顺序）

1. **R1 · 修 CRLF（地基）**：`.gitattributes + renormalize` 一次性提交 → 预算门恢复真实余量，四路字节不再漂移。
2. **R2 · 单文件版内嵌 chunks（地基）**：build 拼入 chunks → 单文件=全量，双版本归一；预算上限合法上调至 ~12.5MB（`elda budget --reason "单文件全量化"`）。
3. **R3 · 以分片版为主力继续扩内容**：线上已是分片版；每次内容批只要 chunked 预算有余量即可推进，单文件版体积上限放宽后二者同步。
4. **R4 · 内容批次节奏**：按既有口径每批 250~450 节点 / 20~40 事件，逐批过 39 检查器 + smoke + bu，节点从 5,580 起步向 8,000~10,000 推进；dn_*.js 已分区（128 文件），最大单文件 dn_story_blueprint.js 568KB（单行 JSON nodeIndex）——若继续膨胀可在 R2 后拆蓝图为按卷文件。
5. **R5 · 新增两个检查器**：`c_nodecover`（单文件版节点覆盖==全量）、`c_crlf`（发布文件禁 CRLF）→ 把本次两个隐患变成 ci FAIL，防止复发。

### 3.4 稳定性保障（现状盘点）

- 已有：39 检查器、smoke_test.py、四路字节、budget 门、CI（GitHub Actions）、pre-commit 钩子、旧档兼容（saveVersion=48 / applyDefaults 兜底）。
- 缺口：无"单文件版覆盖"检查、无 CRLF 检查、无运行时控制台错误告警 → R5 补齐。
- Python 工具链（用户关注点）：`elda.py` 命令族完整（ci/text/content/schema/budget/serve/volume…）；历史"内联 python 中文炸 / Grep 工具不可用 / PowerShell 禁 &&"等坑已固化在 elda-ci-guard references\pitfalls.md。本轮新增 `tools\health_check.py` 把常用探查合并为一条命令（见 §四）。

## 四、工具完善（本轮交付）

用户要求"对文件夹拜访和读取方式等工具进行完善补充，做成最方便读取的方式"。本轮新增两个只读/低风险工具，均已实测：

### tools\health_check.py（一键地基体检，只读）

```
python -X utf8 tools\health_check.py             # 人类可读体检报告
python -X utf8 tools\health_check.py --json      # JSON（供程序消费）
python -X utf8 tools\health_check.py --quick     # 只跑 A/B/C 块
```

输出：发布文件大小/CRLF/节点覆盖 → src 体积分布 → 预算余量 → git 状态/最近提交 → 结论提示（自动标注超预算、缺节点、CRLF）。**以后每轮开工/收尾跑一条即可拿全貌。**

### tools\normalize_lf.py（发布文件 LF 规范化，幂等）

```
python -X utf8 tools\normalize_lf.py             # 规范化发布文件+src+chunks
python -X utf8 tools\normalize_lf.py --check     # 只报告不改
python -X utf8 tools\normalize_lf.py --publish   # 只转 5 个发布文件
```

用途：git pull/rebase/checkout 后、跑 elda ci 前执行一次，消除 CRLF 虚增导致的预算误报。注意：当前 git 索引中发布文件为 CRLF，直接转 LF 会产生 git diff（属 F1 修复批内容，需独立提交）。
