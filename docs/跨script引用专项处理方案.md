# 跨 script 引用专项处理方案（52 项）

> 2026-09-08 · 检测器：c_refhealth 跨 script 专项 · 现状数据：52 项（ATTR_CN / ATTR_DESC / CHURCH_BOARD / FEATS_V51 / SKILLS_V55 / ARC_V55 / CAREER_HUB_V57 等顶层 let/const）

## 一、问题本质（JS 语义真相）

浏览器中多个 `<script>` 标签共享**同一个全局环境**，它由两层组成：

| 层 | 承载 | 示例 |
|---|---|---|
| 全局声明式环境 | `let` / `const` / `class`（全局词法绑定） | `const FEATS_V51 = {...}` |
| 全局对象环境 | `var` / `function` / `window.X =`（window 属性） | `var x = 1`、`window.COMBAT = ...` |

标识符解析顺序：**声明式环境 → 对象环境**。

因此 `script1` 定义 `const FEATS_V51`，`script4` 裸引用 `FEATS_V51` —— **只要 script1 先执行完，解析必然成功**。这是合法、标准、可工作的代码模式，与"跨文件 import"是同一语义的不同载体。

**结论：52 项在当前页面加载顺序下不是 bug，是结构性风险。**

## 三、风险分级（什么情况下会真炸）

| 场景 | 触发条件 | 后果 | 概率 |
|---|---|---|---|
| 单文件当前顺序 | — | 无（已实证） | 不触发 |
| **TDZ 顺序颠倒** | 某 script 的**顶层立即执行代码**引用了尚未初始化的 const（script 顺序调整） | ReferenceError（暂时性死区） | 低，重构/手工调整时可能 |
| **重构收敛** | 未来把 const 包进 IIFE / 改 ES 模块 / 拆加载 | 全部跨 script 裸引用静默失效 | 高——这是 V58 教训（const 定义 + window.X 引用 → undefined）的反面镜像 |
| **分片版加载** | game_chunked.html 的 chunks 动态加载顺序与单文件不一致 | 部分数据对象为 undefined | 中——分片版是独立加载路径 |
| **工具互操作** | Node 脚本 / 测试 / 未来工具想读数据对象 | `window.FEATS_V51` 为 undefined | 确定——const 不挂 window |

## 四、方案对比

### 方案 A：定义处加 window 显式导出（推荐）

做法：52 个 `const X = {...}` 定义尾部追加 `window.X = X;`，**引用处零改动**（裸引用会回退解析到 window 属性）。

原理：改后 `FEATS_V51` 从"声明式环境绑定"变为"对象环境属性"；所有现有裸引用沿"声明式（无）→ 对象环境（有）"仍解析成功；且 window 属性无 TDZ、可互操作、分片版可加载。

| 维度 | 评估 |
|---|---|
| 改动面 | 仅定义处 52 行（每行加一条导出语句），引用处 0 改动 |
| 与既有模式统一 | 与 243 个 window 导出对象完全一致（eldacheck PASS 251 项同款） |
| 检测结果 | 专项 52 → 0，转健康 PASS；未来有守护 |
| 风险 | ①同 script 内"定义前裸引用"：原 TDZ（游戏能跑说明不存在）改后变 undefined——需扫描确认无；②名字冲突：需扫描确认 52 名无 var/function 重复声明 |
| 回滚 | 备份 + 幂等 marker，逐批可逆 |

### 方案 B：保持现状 + 检测降级为 INFO

零改动，承认其合法性（跨 script 共享全局词法作用域是标准行为），c_refhealth 专项降级为普通 INFO。

| 维度 | 评估 |
|---|---|
| 风险 | 结构性脆弱永存：重构/分片/工具互操作三类风险零保护 |
| 成本 | 最低 |
| 适合 | 短期不打算动 engine，只想消噪 |

### 方案 C：IIFE + 显式导出（彻底收敛）

把 52 个 const 包进 IIFE，window 导出；**同 script 内所有引用也要改 window.X**（IIFE 内 const 对同 script 顶层其他代码不可见）。

| 维度 | 评估 |
|---|---|
| 改动面 | 定义处 52 + 同 script 引用 N 处（引用改动量翻倍） |
| 收益 | 命名空间最干净，与 V58 的 15 项 IIFE 收敛同方向 |
| 风险 | 最高——引用改动多、回归面大，需多批验证 |
| 适合 | 未来做"全库命名空间收敛"总工程时并入，单独做性价比低 |

### 方案 D：数据块前置（仅治顺序）

把 52 个 const 移到 script1 顶部。只消除 TDZ 顺序风险，不解决脆弱耦合与互操作，且移动代码风险高于方案 A。**不推荐。**
